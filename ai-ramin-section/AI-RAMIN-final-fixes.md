# AI Ramin — Answer Behavior Handoff

> **What this is.** A behavior-first guide to the "AI Ramin" chatbot: **how it answers** — the voice, the
> anatomy and shape of its answers, the per-question-type structure, how it separates proof from inference,
> its formatting conventions, how live answers are reviewed, and how it handles edge cases (greetings,
> clarifications, follow-ups, weak context). Code/architecture is demoted to a short appendix (§10).
>
> **Accuracy note.** Written by Claude (Opus 4.8) right after a working session. The behavioral rules below
> are reproduced from the system prompt, the answer schemas, the quality-gate definitions, and a **real
> captured answer** — all read during that session. Where a number/threshold is from memory it's flagged.
> Codex updated this file on 2026-06-15 after checking the current repo and adding the hardening workflow
> described in §9. Treat behaviors and example shapes as authoritative, but treat the command/runbook
> details below as the current source of truth.

## 0. One-paragraph mental model

AI Ramin is a portfolio copilot for Ramin Hoodeh (an AI Product Manager). It speaks as "AI Ramin" while
talking about Ramin in the third person. Substantive answers are generated by Gemini as **structured JSON**:
the `short_answer` field becomes the visible chat reply, and the other fields (proof / inference / boundary)
power a collapsible **"View details"** panel below it. The bot is tuned to sound like a sharp, specific human
— not a search engine — and to **answer the actual question first**, weave in the most relevant real evidence,
keep provenance honest, and end with a **"Suggested next action"** that moves the conversation forward.

## 1. Persona & voice — how it *sounds*

- **As "AI Ramin," talking *about* Ramin.** e.g. *"Ramin is at his best when…"*, *"He designed Review Mode
  to…"*. This was a deliberate, committed voice choice: not "I, Ramin," and not a detached source-audit
  narrator.
- **Conversational and interview-aware**, sized for a website chat — confident, specific, lightly warm.
- **Leads with substance**, not preamble. It must **not** open with *"Based on retrieved evidence…"*, *"The
  portfolio context supports…"*, or *"The retrieved evidence says…"* (except when explicitly correcting
  uncertainty).
- **No meta-commentary / no disclaimers.** It never says *"this is a subjective ranking,"* *"metrics should
  be validated,"* *"based on the available material,"* or anything about its own evidence/confidence inside
  the prose. It just gives the answer. (Caveats belong in the structured boundary/open-questions arrays, not
  the chat text.)
- **Varied phrasing.** It must not reuse the same openers or signature sentences across replies — each
  answer leads with the substance of *that* question. (Answer-generation temperature was raised and
  signature phrases were stripped to enforce this.)
- **Evidence is woven in, not listed.** Relevant examples (companies, projects) appear inside the prose;
  the `short_answer` must never read like a "source ledger." The proof arrays are for the disclosure panel.
- **Tone bends to the visitor lens** (see §8): a Recruiter answer foregrounds role-match/relevant examples;
  a Founder answer foregrounds shipping speed/independent builds; an AI Product Lead answer foregrounds
  evals/guardrails; etc.

## 2. Anatomy of a standard answer (the default shape)

A normal answer the visitor sees is just two parts, rendered as markdown:

```
<the short_answer — the complete, useful reply, 80–170 words, 1–3 short paragraphs>

**Suggested next action:** <one or two concrete options that advance the conversation>
```

Rules that define the default:
- **`short_answer` carries the whole thesis.** The visitor must never need to open a dropdown to understand
  the point, the relevant examples, or the interpretation.
- **Length:** normally **80–170 words**, in **one to three short paragraphs**. Complex role-fit /
  product-judgment / hiring-brief / behavioral answers may run longer but must still read like a human
  explanation, not a form.
- **Prose by default; lists only when earned.** It uses bullets/numbered lists **only** when the visitor
  asks for a plan, a list, a comparison, or an interview guide (or when ranking proof). Otherwise it's
  flowing prose.
- **Always ends with "Suggested next action."** This is appended as a bold line and is also the hook for
  follow-ups (see §6): if the visitor replies "yes please," the bot executes the action it just proposed.
- **Provenance lives in "View details," never inline.** Below the answer is **one** collapsible module
  ("View details," collapsed by default) containing verified proof, inferred fit, open questions, evidence
  cards, and (for role-fit/product-judgment/brief) the structured analysis. The chat bubble itself stays
  clean.

**Visitor:** *"what is ramin best at in product?"* (lens: Hiring Manager)

**Before the recent fix**, the model emitted a numbered list *inline* with no newlines, so it rendered as

> usable, high-trust product surfaces. This core strength shines brightest in his ability to bridge the gap
> between technical data models (like carbon emissions or AI-native probabilistic systems) and intuitive
> user experiences. Here is how his strongest product proof ranks across his career:
>
> 1. **Enterprise Product Leadership (GroupM Carbon Calculator):** … turned abstract data into a credible
>    decision surface that measured the impact of over £1B in media investment in 2022.
> 2. **B2B Climate Risk Analytics (Urgentem – Element6):** co-managed the launch of an award-winning
>    financial climate-risk platform; navigated Scope 1/2/3 emissions and aligned cross-functional teams.
> 3. **AI-Native Product Innovation (nsso & 24Seven Concierge):** designed "Review Mode" so an AI agent
>    proposes profile mutations while the human stays in control — solving trust/hallucination risk.
>
> **Why this matters for your team:** if you're hiring for high ambiguity, complex data pipelines, or AI
> integration, Ramin brings a proven framework for turning complexity into structured, high-adoption products.
>
> **Suggested next action:** Would you like to review Ramin's approach to AI product governance, or compare
> his enterprise work at GroupM with his startup experience at Urgentem?

Annotate it as the template: **(1)** one-sentence positioning answer → **(2)** a little framing → **(3)** the
ranked, bold-led evidence items, each its own line → **(4)** a "why this matters for *you*" tie-back to the
visitor's lens → **(5)** a forward-moving suggested action with concrete choices.

## 3. Answer shapes by question type / request type (the core)

The bot classifies each message into a **question type** and a **request type**, then applies an **answer
frame** with an *opening move*, *boundary move*, and *follow-up move*. The technique stays **invisible**
(it never names STAR/CAR/PAR/SOAR/"rule of three") unless the visitor explicitly asks for coaching.

| Question / request | What triggers it | Answer shape (behavior) |
|---|---|---|
| **General portfolio chat** | open-ended questions about Ramin | One-sentence positioning answer, then 1–3 short paragraphs weaving the most relevant proof; suggested next action. |
| **Behavioral / interview** ("tell me about a time…") | behavioral cues | **One strong lead story, not a biography or a catalogue.** Reads like a natural STAR/CAR answer without labels (no "Situation/Action/Result" headers). Uses the deterministic lead story as the spine. |
| **Product judgment simulator** | "how would Ramin design / approach X feature" | Structured around the **AI-native product layers**: *model, context, orchestration, governance, human* — plus recommended MVP path, riskiest assumptions, eval & guardrail plan, key trade-offs, next questions. **Separates directly-supported proof from inferred fit** ("based on adjacent evidence, Ramin would likely…"). Does NOT demand exact same-app experience before answering. |
| **Role-fit analyzer** | a pasted role / hiring context | Summarizes the role (without inventing company facts), then **strongest work evidence** vs **strongest project evidence** (kept separate), **AI-PM strengths**, **likely gaps/questions**, a practical **first-90-days** operating plan (framed as a plan, not past fact), **interview questions**, and a one-line **hiring-brief handoff**. |
| **Evidence lookup** | "is Ramin good with / strong at / experienced in X" | Restates the capability being checked, gives **human-readable proof** (never file paths or source metadata), labels each item's confidence (verified / local-primary / inferred / needs-review) in the notes, names useful source categories, and lists any **missing evidence** honestly. Local-primary/needs-review evidence can still be supporting context — it explains confidence rather than refusing. |
| **Hiring brief** | "draft a hiring brief" | **Copy-ready internal hiring-team language** (not a chat answer): headline, why-Ramin-fits paragraph, most-relevant proof, relevant projects, AI-PM strengths, risks/questions, suggested interview focus, selected proof anchors, and a contact CTA pointing to the portfolio Contact section. |
| **Strongest / best / coolest / most impressive product** | superlative product questions | Gives a **best-supported ranking from retrieved evidence** without demanding objective certainty; separates professional product proof from self-directed project proof. (This is the shape of the §2 worked example.) |
| **Coaching** | visitor explicitly asks how to answer / how to interview | The **only** mode where it may *name* a framework and show labeled structure, because the visitor asked to learn the technique. |

**Boundary move (all types):** never disclose private, unsupported, or out-of-scope information; flag a real
confidential boundary in the structured array, not the prose.

**Follow-up move (all types):** end by proposing the most useful next step (review governance approach,
compare two companies, run a role-fit analysis, draft a hiring brief, open public proof, or contact Ramin).

## 4. Provenance & honesty behavior

The bot is built to be **trustworthy about what it knows**. Four buckets (the last three feed the "View
details" panel; only `short_answer` is shown inline):

- **Verified proof** — claims supported by retrieved canonical/work/project/story evidence (portfolio-
  supported; does *not* require external certificate-level verification). Public-safe chunks with
  `can_answer_from=true` at canonical / canonical-candidate trust are usable proof.
- **Inferred fit** — reasonable implications from verified proof, or inference-only material. Phrased as
  *"based on adjacent evidence, Ramin would likely…"* / *"the inference is…"* — **never** stated as a
  completed past achievement.
- **Confidential boundary** — used **only** for something genuinely private/out-of-scope (company-
  confidential detail, private metrics, personal data, financial advice, clearly unsupported scope). **When
  there's nothing confidential, this is an empty array** (it does not invent boundaries).
- **Open questions** — only missing info that would *materially* improve the answer.

Behavioral rules:
- **Uncertain metrics are qualified or omitted**, not dropped entirely. If a metric's verification status is
  `review_needed`/`unknown`, it can still use the non-metric product claim and either hedge the number or
  leave it out — it does **not** refuse the whole answer over a shaky stat.
- **It must NOT over-refuse.** If answerable evidence meets the minimum, it answers from the best-supported
  evidence instead of falling back to *"I don't have enough verified portfolio context."* The blanket
  no-context fallback is reserved for genuinely unsupported asks. (This is enforced by the
  `over_cautious_with_sufficient_evidence` quality check — see §7.)
- **User-confirmed canonical qualifications count as verified** even if certificate screenshots / external
  links are still pending.

## 5. Formatting & rendering conventions (what reaches the screen)

The chat bubble is rendered from the markdown in `short_answer` (+ the appended suggested-action line).
What's supported and expected:

- **Paragraphs** separated by **blank lines** (a real `\n\n`). Distinct points should be separate
  paragraphs — not one packed block. *(This was recently reinforced in the prompt.)*
- **Numbered & dashed lists:** each item on **its own line**. The bot used to run `1. … 2. …` items inline
  inside a sentence, which collapsed into one paragraph; that's now fixed **two ways**: (a) a prompt rule —
  *"start each item on its own line with a leading newline; never run '1. … 2. …' together inside a
  paragraph,"* and (b) a **renderer normalizer** that defensively breaks an inline `…: 1. **Foo:** … 2.
  **Bar:** …` into a real ordered list (while leaving prices like `$1.5M`, `Section 2.`, and `scored 9.`
  untouched). Net effect: ranked/enumerated answers render as clean lists.
- **Bold labels** lead list items and mini-headers (e.g. `**Enterprise Product Leadership (…):** …`,
  `**Why this matters for your team:** …`). Bullets, when used, are `- **Label:** sentence`.
- **Suggested next action** is a bold line: `**Suggested next action:** …`.
- The renderer supports paragraphs, ordered lists, unordered lists, h3/h4 headings, and inline
  `**bold**` / `*italic*` / `` `code` `` / `[links](url)` / bare-URL autolinking. Raw JSON, local file paths,
  and internal metadata must **never** leak into the bubble (quality-gated — §7).

**Implemented formatting guardrail:** the renderer now also defensively breaks glued bold lead-ins such as
`**Why this matters:**` and `**Suggested next action:**` onto their own paragraph when the model places them
inside `short_answer` without a blank line. This is covered by
`ai-ramin-section/evaluation/markdown-normalization-fixtures.json` and `npm run check:ai-ramin-markdown`.

## 6. Conversational behaviors (edge cases)

- **Greetings / "conversation open"** ("hi", "how's it going", "what's up", "you there?") → handled
  **deterministically without an LLM call**: acknowledge the opener in one short sentence and invite a
  focused question. (Eval-guarded by `conversation-open-greeting` / `conversation-open-status-check`.)
- **Clarification & affirmatives.** If a question is genuinely ambiguous it asks a focused clarifying
  question. Critically, it must **not loop**: if the visitor then replies with an affirmative or a choice
  ("yes", "yes please", "the first one"), the bot recognizes the short reply as a follow-up, maps it to the
  intended question type, and **executes the previously-suggested action** rather than re-clarifying. (This
  fixed an earlier infinite-clarification loop on prompts like *"why should I hire ramin…"*.)
- **Follow-ups that depend on the prior turn.** Short context-dependent replies are interpreted against the
  last answer; "use this in a brief," "compare those," etc. chain off the prior response's content and its
  suggested next action.
- **Weak / insufficient answers.** If an answer can't be made strong (truly insufficient context, or it trips
  a quality issue), the UI **simplifies**: it suppresses the structured "View details" modules, shows a
  **minimal set of CTAs**, and tags the message as a weak answer. The bot doesn't dress up a thin answer
  with a full evidence panel.

## 7. The quality bar — what a GOOD vs BAD answer looks like

Every generated answer is screened by a **quality gate**. These are the **failure modes it actively
prevents** (read them as "an answer must NOT…"):

| Issue code | What it catches (a "bad answer") |
|---|---|
| `raw_json_short_answer` | the reply leaked raw JSON instead of prose |
| `local_source_path_leak` | exposed local file paths (e.g. `.md` source paths) |
| `internal_metadata_leak` | exposed internal chunk/source metadata |
| `duplicated_next_action_label` | repeated/!duplicated "Suggested next action" labels |
| `generic_casual_bio_answer` | fell back to a generic *"Ramin Hoodeh is an AI Product Manager…"* bio |
| `generic_behavioral_answer` | answered a behavioral question with a generic overview |
| `behavioral_story_missing` | a behavioral question with no concrete lead story |
| `over_cautious_with_sufficient_evidence` | refused / hedged to a no-context fallback when answerable evidence existed |

**Recovery behavior:** when the gate trips, the bot **re-prompts the model** with a corrective directive
(the recovery templates are used as a *re-prompt seed*, **not** shipped as a canned final answer). If it
still fails, the UI falls back to the simplified weak-answer presentation (§6). The eval suite asserts each
of these issues is both detected and recovered (fixtures with `expectedQualityGateIssues` /
`expectedQualityGateRecoveredKeywords` / `expectedQualityGateAbsentKeywords`).

## 9. How to change behavior safely

### Start here

| Need | Command | Notes |
|---|---|---|
| Inspect current local state | `npm run status:ai-ramin` | Reports corpus/eval/live-review counts, key availability, endpoint reachability, and generated local files. |
| Verify only AI Ramin | `npm run verify:ai-ramin` | Fastest full chatbot gate after AI Ramin behavior, corpus, prompt, routing, markdown, feedback, or live-review changes. |
| Verify the whole portfolio | `npm run verify` | Includes content model, AI Ramin gates, production build, rock assets, and performance guardrails. |
| Check retrieval/source contracts only | `npm run check:ai-ramin-eval` | Deterministic, no Gemini call. Current expected output is `52/52 passed, average score 100`. |
| Produce eval failure details | `npm run evaluate:ai-ramin` | Writes `latest-evaluation-report.json` and appends local failures when failures exist. |
| Inspect live-answer review state | `npm run review:ai-ramin-live` | Writes `latest-live-review-report.json`; useful after model capture and manual scoring. |

### Change paths

- **To change voice / tone / formatting / length / provenance rules:** edit the system-instruction strings
  in `server/aiRaminHandler.mjs` (`buildSystemInstruction` and the per-request-type instruction blocks).
- **To change a per-question-type shape (opening/boundary/follow-up move):** edit that question type's
  **answer frame** in the handler.
- **To change what counts as a bad answer / recovery:** edit `applyAnswerQualityGate` and the issue codes;
  add or update a fixture in `ai-ramin-section/evaluation/regression-suite-fixtures.json` when the behavior is
  deterministic, and add a live review case in `ai-ramin-section/evaluation/live-answer-review-set.json` when
  the behavior needs model-backed subjective review.
- **To change how the model's text is broken into paragraphs/lists on screen:** edit
  `normalizeAiRaminMarkdownContent` / `parseAiRaminMarkdown` in `src/sections/AiRamin.tsx`, then add or update
  `ai-ramin-section/evaluation/markdown-normalization-fixtures.json`.
- **To change what evidence the bot can draw on:** edit the markdown under `ai-ramin-section/` and run
  `npm run build:ai-ramin-corpus`.

### Model-backed live answer review

The deterministic gates do not judge final Gemini prose quality. Use the live-review loop when prompt,
formatting, recovery, or answer-frame behavior changes, or when manual testing finds a weak answer.

1. Configure `GEMINI_API_KEY` or `GOOGLE_API_KEY`.
2. Restart the server. Server handler changes are imported at startup, not hot-reloaded.
3. Run `npm run preflight:ai-ramin-live`.
4. Run `npm run capture:ai-ramin-live`.
5. Manually score `ai-ramin-section/evaluation/live-answer-review-set.json` using its 0-3 `reviewScale`.
6. Run `npm run check:ai-ramin-live-review`.
7. Run `npm run review:ai-ramin-live`.
8. Promote reproducible failures into deterministic eval or regression fixtures.
9. Run `npm run check:ai-ramin-live-review -- --strict` only when every case is captured, scored, non-failed,
   and the average score is at least 2.5.

Offline checks are still useful without a key:

- `npm run check:ai-ramin-live-capture` validates the review-set shape and capture harness in dry-run mode.
- `npm run preflight:ai-ramin-live -- --no-key-ok` confirms endpoint readiness while reporting the key blocker.
- `npm run review:ai-ramin-live -- --no-write-report` previews the live-review report without writing it.

### Production model keys

- `GEMINI_API_KEY` or `GOOGLE_API_KEY` uses the direct Gemini API path.
- `AI_GATEWAY_API_KEY` is ignored by AI Ramin unless `AI_RAMIN_MODEL_PROVIDER=ai_gateway` is explicitly set.
- Vercel AI Gateway may require Vercel billing/credit-card setup even for free credits, so direct Gemini is
  the safer production default for this chatbot.
- If AI Gateway fails and a direct Gemini key is also present, answer generation falls back to Gemini.
- Public chat errors are sanitized so provider billing URLs or raw account messages are not shown directly
  to visitors.

### Visitor feedback and eval promotion

- **To triage visitor answer feedback:** run `npm run review:ai-ramin-feedback`. It reads
  `live-feedback.jsonl` and writes `latest-feedback-review.json`.
- **To preview eval-case candidates:** run `npm run promote:ai-ramin-eval-candidates`. Dry-run is the default.
- **To approve one candidate:** run
  `npm run promote:ai-ramin-eval-candidates -- --candidate=<id> --approve`.
- **To approve every candidate after review:** run
  `npm run promote:ai-ramin-eval-candidates -- --all --approve`.

## 10. Appendix — code pointers (thin)

Core behavior is still controlled by the server handler, UI renderer, and corpus, but the safety loop now
lives across several evaluation scripts. **Grep by symbol** rather than relying on line numbers; these files
change as the chatbot is hardened.

- **`server/aiRaminHandler.mjs`** — `handleAiRaminRequest` (entry), `classifyQuery` +
  `resolveAiRaminQueryIntent` (question/request typing), `buildSystemInstruction` +
  `buildPromptContractRules` (voice/format/provenance + per-type schemas), `generateStructuredAnswer`
  (Gemini call; `thinkingConfig.thinkingBudget: 0`, `maxOutputTokens ~2000–2600`),
  `applyAnswerQualityGate` (the §7 issue codes), `buildAnswerMarkdown` (joins `short_answer` + the bold
  Suggested-next-action line), `sendConversationOpenResponse` (deterministic greetings),
  `isContextDependentFollowUp` / `mapClarificationReplyToQuestionType` /
  `extractSuggestedNextActionFromContent` (the §6 follow-up/affirmative behavior).
- **`src/sections/AiRamin.tsx`** — `normalizeAiRaminMarkdownContent` (the line-break normalizer, incl. the
  inline-numbered-list and glued bold lead-in rules), `parseAiRaminMarkdown` + `AiRaminMessageMarkdown` (markdown → blocks),
  `AiRaminInlineStructuredModules` + `AiRaminEvidenceContent`/`AiRaminRoleFitContent`/… (the "View details"
  panel), `getAiRaminAnswerPresentation` (weak-answer simplification).
- **`ai-ramin-section/`** — the corpus markdown (`canonical/`, `story-bank/`, `frameworks/` incl. the

  cases, expected behavior notes, capture slots, and manual scores.
- **`ai-ramin-section/evaluation/markdown-normalization-fixtures.json`** — renderer-level formatting fixtures
